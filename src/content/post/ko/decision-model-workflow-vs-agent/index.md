에이전트가 모든 일을 처리하는 구조가 당연해 보이지만, 기업 업무를 뜯어보면 상당수는 매번 같은 단계를 밟는 일이다. 이 글은 최근 다시 주목받는 **결정 모델(Decision Model)**을 중심으로, 에이전트에게 맡기던 일을 결정론적 워크플로로 되돌리는 접근을 정리한다. 한 실무자가 SNS에 공유한 경험담을 바탕으로, 결정 모델 Jev에 대한 공개 자료를 함께 덧붙였다.

## 1. 결정 모델이란 — 글 대신 확률로 답하는 모델

결정 모델은 텍스트를 생성하지 않고, **미리 정한 질문에 확률로 답하는** 모델이다. 카너먼의 『생각에 관한 생각』에 빗대면 일반 LLM과 에이전트는 느리고 신중한 System 2, 결정 모델은 빠르고 직관적인 System 1에 해당한다. 그래서 System One 모델이라고도 부른다.

대표 사례는 TypeSafe AI의 **Jev**다. 2026년 9월 15일 얼리 액세스로 공개됐고, 애플리케이션이 상태와 타입이 정해진 질문을 넘기면 선택지·점수·참/거짓 같은 값을 확률과 함께 돌려준다.

| 항목 | 일반 LLM | 결정 모델 (Jev) |
| --- | --- | --- |
| 출력 | 자유 텍스트, 파싱·검증 필요 | 스키마로 정의한 타입 값 |
| 생성 방식 | 토큰을 하나씩 순차 생성 | 선언한 질문들을 한 번에 병렬 평가 |
| 신뢰도 | 확률을 물어봐도 과신하는 경향 | 출력마다 보정된 확률[^calibration] |
| 지연 (벤더 발표) | 수 초 이상 | 70–500 ms |
| 맞는 일 | 대화, 코드 생성, 글쓰기 | 분류, 라우팅, 점수화, 검증, 가드레일 |

원문 작성자는 Jev가 문서 이미지 한 장에 대한 질문 여섯 개에 0.5초 안에, 약 0.1센트로 답한다고 소개한다. 속도·비용 수치는 대부분 TypeSafe 자체 평가라 실제 업무에 맞춰 직접 검증해야 한다.

> 주의: "환각이 없다"는 말은 스키마 밖의 값이나 타입 오류를 낼 수 없다는 뜻이지, 틀린 결정을 내리지 않는다는 뜻이 아니다.

## 2. 에이전트 vs 결정 워크플로 — 같은 일을 어떻게 처리하나

```text
[에이전트] 실행마다 계획을 새로 세운다
  입력 → LLM(계획·판단) ⇄ 도구(검색·실행)   ← 끝났다고 판단할 때까지 반복
        → 답
  이번 실행의 계획: 웹 검색 → 파일 읽기 → 다시 검색 (다음 실행엔 달라질 수 있음)

[결정 워크플로] 정해진 단계를 그대로 밟는다
  입력 → ① 도구 (PDF → 이미지)
       → ② 결정 · System One (인감 / 서명 / 날짜 질문에 확률로 답)
       → ③ 코드 (규칙 · 임계값)
       → ④ 분류 → 적합 | 사람 검토 | 부적합
  (워크플로 자체는 에이전트가 한 번 작성하고, 사람이 확인한 뒤 머지)
```

| 구분 | 에이전트 | 결정 워크플로 |
| --- | --- | --- |
| 계획 | 실행할 때마다 새로 세움 | 미리 정해진 단계 |
| 같은 일 처리 | 매번 다른 경로 | 매번 같은 경로 |
| 비용·속도 | 느리고 비쌈 | 빠르고 쌈 |
| 불확실할 때 | 스스로 판단해 계속 진행 | 확신이 없으면 사람에게 넘김 |

결정 모델이 주목받는 이유는 바로 이 점이다. **에이전트에게 맡기던 반복 업무를 다시 워크플로로 돌려놓을 수 있다.**

## 3. 예시 — 거래처 등록 서류 20건 검토

거래처 등록을 위해 사업자등록증, 법인 등기사항전부증명서, 통장 사본 20건을 검토한다고 하자. 일부 서류는 날짜를 고친 흔적이 있거나 인감이 빠져 있다. 에이전트로도 처리할 수는 있지만 느리고 비싸며 매번 다르게 처리한다.

원문 작성자가 같은 일을 워크플로로 구성한 단계는 다음과 같다.

1. PDF를 이미지로 변환한다.
2. Jev가 인감, 서명란, 발급일을 **각각 따로 묻는 질문**에 확률로 답한다.
3. 사업자등록번호 검증처럼 규칙이 정해진 항목은 코드가 계산한다.
4. 코드가 확률을 임계값과 비교해 적합 / 부적합 / 사람 검토로 나눈다.
5. 확신이 없는 서류는 사람에게 넘긴다.
6. 마지막에 LLM을 한 번만 호출해 보고서를 쓴다.

결과는 약 20초, 2센트로 20건 중 19건을 맞혔고, 처음 보는 서류 4장도 모두 맞혔다고 한다.

### 3-1. 질문을 쪼개는 이유 — 정확도

두 항목을 한 질문에 묶으면 결과가 흔들린다. 원문 사례에서 인감과 서명이 **모두 없는** 서류에 "인감과 서명이 있는가"를 묻자 0.93이 나왔고, "모든 서명란이 채워져 있는가"로 바꾸자 0.07로 제대로 나왔다. **질문 하나에는 판단 하나만 담는다.**

### 3-2. 규칙은 코드에 맡긴다

결정 모델은 사업자등록번호 체크섬 같은 규칙을 알지 못한다. 규칙으로 답이 정해지는 항목은 코드로 계산하고, 모델에는 눈으로 보고 판단해야 하는 것만 묻는다. 결국 **워크플로를 잘 짤 수 있도록 하네스[^harness]를 구성했는가**가 결정 모델 도입의 성패를 가른다.

## 4. 에이전트가 워크플로를 짠다 — 학습 루프

지금까지 워크플로는 사람이 만들었지만, 이제는 Claude Code나 Codex 같은 하네스 안에서 에이전트가 직접 만들 수 있다.

```text
처음 보는 일 → 에이전트가 처리 → 배운 내용을 기록
      ↓ (같은 일이 반복되면)
단계를 워크플로로 작성 → git 레포에 PR → 사람이 확인 후 머지
      ↓
다음부터는 워크플로가 먼저 실행
      ↓
확신하지 못한 건은 에이전트로 되돌아가 다시 학습 재료가 됨
      ↓
잘 동작하는 워크플로는 유지, 그렇지 않은 워크플로는 되돌림
```

배운 내용과 워크플로가 **파일로 저장**되므로 특정 도구에 묶이지 않는다. Claude Code가 만든 워크플로를 Codex에서 실행할 수도 있다.

## 5. 그래도 에이전트가 필요한 일

단계를 미리 알 수 없는 일에는 여전히 에이전트가 필요하다. 조사, 글쓰기, 디버깅이 대표적이다. 코딩 에이전트가 잘 동작하는 것도 다음 단계로 넘어가기 전에 코드가 실제로 돌아가는지 확인할 수 있기 때문이다.

원문 작성자가 한 달간 써 보고 정리한 역할 분담은 다음과 같다.

| 일의 종류 | 맡길 모델 |
| --- | --- |
| 처음 보는 일, 워크플로 작성 | Claude, GPT, Gemini 같은 최상위 모델 |
| 반복되는 판단 | 결정 모델 |
| 반복되는 생성 | 고속 추론이 가능한 저가 플래시 모델 |

이렇게 나누면 낮은 비용으로 큰 효과를 낼 수 있고, 사전 지시와 시스템을 얼마나 잘 갖춰 두느냐가 AI 자동화의 성패를 가른다는 것이 원문의 결론이다.

## 마무리

- 기업 업무의 상당수는 매번 같은 단계를 밟는 "워크플로"이고, 이런 일은 에이전트보다 결정 모델 기반 워크플로가 빠르고 싸고 일관적이다.
- 워크플로의 핵심은 **질문 하나에 판단 하나**, **규칙은 코드로**, **확신이 없으면 사람에게**다.
- 에이전트는 처음 보는 일을 처리하고, 반복되는 일을 워크플로로 적어 넘기는 역할로 옮겨 간다.

### 예상 질문

- **Q. 결정 모델은 환각이 없다는데 그대로 믿어도 되나?** 스키마 밖의 값을 낼 수 없다는 의미일 뿐, 판단이 틀릴 수는 있다. 그래서 임계값과 사람 검토 경로를 반드시 둔다.
- **Q. 확률이 왜 중요한가?** 확률이 보정되어 있어야 "0.95 이상만 자동 처리, 나머지는 사람에게" 같은 규칙을 안전하게 걸 수 있다. 확률 없이 정답만 주면 어떤 건을 의심해야 할지 알 수 없다.
- **Q. 모든 일을 워크플로로 바꾸면 되지 않나?** 단계를 미리 알 수 없는 조사·글쓰기·디버깅은 에이전트가 맡아야 한다. 결정 모델은 설명이나 근거를 써 주지 않는다는 한계도 있다.

[^calibration]: 보정된(calibrated) 확률은 모델이 0.9라고 답한 건들을 모아 보면 실제로 약 90%가 맞는다는 뜻이다. 일반 LLM은 확률을 물어보면 실제보다 자신 있게 답하는 경향이 있어 이 값을 기준으로 자동화하기 어렵다. 보정된 확률이 있어야 임계값을 정해 확실한 건은 자동 처리하고, 애매한 건만 사람이나 더 비싼 모델로 넘기는 구조를 만들 수 있다.
[^harness]: 하네스는 모델을 감싸서 실제 일을 하게 만드는 실행 환경이다. 어떤 도구를 쓸 수 있는지, 지시와 배운 내용을 어디에 저장하는지, 결과를 어떻게 검증하는지를 정한다. Claude Code나 Codex가 대표적이며, 이 글에서는 에이전트가 워크플로를 작성하고 git으로 관리할 수 있게 해 주는 기반을 가리킨다.
