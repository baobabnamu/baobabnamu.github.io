## 상황 — 멈춰 있던 레거시 수집 기능

ISMS 심사 대비 보안 취약점 개선 작업으로 레거시 서버들을 분석하던 중, 특정 기능이 **미동작 상태**인 것을 발견했다. 담당자도 바뀌고 문서화도 흐릿해진 레거시라, 기능이 멈춘 이유부터 추적해야 했다.

## 1. pmacct 프로세스 점검 — 누락된 인터페이스

과거 사내 컨플루언스 문서를 통해 이 기능이 `pmacct`로 네트워크 트래픽을 집계하는 구조라는 것부터 확인했다.

```bash
ps -ef | grep pmacct
```

실행 경로는 확인됐지만, **모든 네트워크 인터페이스를 추적하고 있는 것이 아니라 몇 개가 누락돼 있었다**. 프로세스 실행 디렉터리 하단의 설정 파일을 확인한 결과, **pmacct 데몬 실행 config 파일을 생성하는 스크립트 중 인터페이스를 지정하는 로직에 오류가 있었다**. 로직을 수정하고 설정 파일을 재생성해 정상 원복했다.

## 2. 집계 스크립트와 MySQL 연동 구조

이어서 트래픽을 집계하는 Perl 스크립트를 분석했다. (사내 보안 정책상 스크립트 자체는 공개할 수 없어 아래 요약으로 대체한다.)

- 스크립트는 `pmacct` 데몬이 60초마다 집계한 통신량을 체크해 MySQL DB에 저장한다.

## 3. DB 연결 복구 — Federated Engine이 끊어진 이유

트래픽 데이터를 저장하는 DB를 분석하는 과정에서, **MySQL Federated Engine으로 원격지 DB 테이블을 참조**하고 있다는 걸 확인했다. 그런데 최근 사내 보안 이슈 대응으로 변경한 DB 패스워드가 이 연결에는 반영돼 있지 않아, 관련 트랜잭션이 모두 Lock에 걸려 있는 상태였다.

별도 API나 Bash 스크립트 없이 **MySQL Trigger를 사용** 중이었다(통신량을 일 단위로 누적 합산하는 트리거, 원격지 DB를 참조해 비교 연산하는 트리거). 문제는 기존에 Federated Table을 만드는 방식이 **DB 패스워드가 바뀔 때마다 테이블을 DROP하고 다시 만들어야 하는 구조**였다는 점이다. 그래서 별도 `CREATE SERVER`로 원격 DB Connection 정보를 주입받는 방식으로 개선했다.

> 주의: Connection 정보는 올바르게 수정했는데도 여전히 연결되지 않았다 — 원인은 DB가 아니라 그 사이 어딘가에 있었다.

## 4. 네트워크 디버깅 — 쿠버네티스 마이그레이션이 남긴 방화벽 구멍

DB 서버의 접근 로그를 확인했지만 별다른 기록이 없었다. 직접 해당 서비스의 웹 서버에 접속해 `telnet` 테스트를 해보니 방화벽 정책 누락이 의심됐다. 확인 결과, **개발팀이 쿠버네티스로 마이그레이션하면서 백엔드 서비스 IP가 바뀌어 방화벽 정책이 누락**돼 있었다.

정책을 추가한 뒤에도 연결은 여전히 되지 않았다. DB 서버 로그를 다시 확인하니 이번엔 Access Denied였다 — **시스템 DB에 접근 가능한 호스트 IP 목록에 새 IP가 빠져 있어서**였다. 이를 추가하고 나서야 정상 접근이 확인됐다.

## 5. 서비스 지연 진단 — PHP 로직과 IDC별 DB 트랜잭션

```sql
SHOW FULL PROCESSLIST;
```

접근은 가능해졌지만, **브라우저에서 관제 페이지를 테스트하니 개발자 도구 기준 1m 20s가 걸렸다**. PHP 코드를 분석한 결과 **IDC 센터별 로직 자체는 동일하고, 변수에 따라 접근하는 DB만 다른** 구조였다. 지연이 발생하는 IDC 센터의 수집 서버에 접속해 DB 트랜잭션을 확인하니, 해당 인터페이스가 수집하는 데이터량이 다른 센터보다 훨씬 많아 지연이 발생하고 있었다.

근본적으로는 개발 단에서 개선이 필요한 구조였지만, 개발 부서는 해당 서비스를 유지보수할 인력이 부족했고 시스템 엔지니어 부서에서 코드를 직접 수정할 수도 없는 상태였다. 그래서 애플리케이션 레벨이 아니라 DB 레벨에서 손볼 수 있는 부분을 찾기로 했다.

## 6. MySQL 튜닝 — InnoDB 버퍼 풀과 커밋 내구성 트레이드오프

튜닝에 앞서 실제로 어떤 설정 파일을 사용하고 있는지부터 확인했다.

```sql
SELECT VARIABLE_NAME, VARIABLE_SOURCE, VARIABLE_PATH
FROM performance_schema.variables_info
WHERE VARIABLE_SOURCE NOT IN ('COMPILED');
```

지연이 발생하는 DB 테이블의 행 수는 약 12만 건이었다. 문제를 좁혀보면 두 가지였다: 12만 건에 달하는 데이터를 모두 DB 버퍼 풀에 올려야 한다는 점, 그리고 다른 IDC 센터보다 고객사가 많은 지점이라 인터페이스당 DB 쓰기량이 많다는 점이다. `my.cnf`에서 다음 값들을 수정했다.

- **innodb_buffer_pool_size: 8G** (기본값 128M) — Grafana로 최근 2주간 해당 DB 서버의 메모리 사용량 추이와 crontab을 확인한 결과, 8G까지는 충분히 확보할 수 있다고 판단했다.
- **innodb_flush_log_at_trx_commit: 2** (기본값 1) — 기본값 1은 커밋할 때마다 redo log를 디스크에 fsync해 커밋된 데이터 유실이 없다. 2로 바꾸면 커밋 시 OS 캐시까지만 쓰고 디스크 fsync는 약 1초 주기로 수행된다. 이 DB의 쓰기는 60초 주기 집계 데이터와 그 시점에 실행되는 트리거 2개 수준이라, 1초치 유실이 생겨도 다음 집계 주기에 다시 채워지므로 허용 범위로 판단했다.
- **sync_binlog: 0** (기본값 1) — 기본값 1은 커밋할 때마다 binlog를 디스크에 fsync해 binlog 유실이 없다. 0으로 바꾸면 binlog fsync 시점을 OS에 맡기게 되어 약 1분 미만의 데이터가 유실될 가능성이 생긴다(예: OS 장애 시 아직 디스크에 쓰지 않은 binlog 유실). 별도 replica를 쓰지 않고 있고, 장애 복원도 binlog 기준으로 하지 않는 구조라 허용 범위로 판단했다.

> 원칙: 커밋 내구성을 낮추는 설정은 성능과 맞바꾸는 유실 범위를 먼저 재고, 그 워크로드가 감당할 수 있는 수준인지 확인한 다음 적용한다.

## 마무리

- "기능이 동작하지 않는다"는 증상의 실제 원인은 pmacct 설정 파일을 생성하는 스크립트 하나의 로직 오류였다 — 레거시일수록 증상과 원인 사이의 레이어가 길다.
- 복구 과정은 프로세스(pmacct) → DB 연결(Federated Engine, 비밀번호) → 네트워크(방화벽, 접근 IP) → DB 성능(InnoDB 설정) 순으로, 레이어를 하나씩 배제해 나가는 흐름이었다.
- 애플리케이션 코드를 고칠 리소스가 없을 때도, DB 설정 레벨에서 손댈 수 있는 여지는 남아 있다 — 다만 그 여지는 대개 내구성·안전성과의 트레이드오프라는 것을 먼저 확인해야 한다.

### 예상 질문

- **Q. Federated Table을 DB 패스워드가 바뀔 때마다 다시 만드는 대신 CREATE SERVER로 바꾼 이유는?** 기존 방식은 패스워드가 바뀔 때마다 테이블을 DROP하고 재생성해야 하는 구조라, 운영 변경(비밀번호 로테이션)이 있을 때마다 수동 개입이 필요했다. CREATE SERVER로 Connection 정보를 분리하면 자격 증명이 바뀌어도 테이블을 다시 만들 필요가 없다.
- **Q. innodb_flush_log_at_trx_commit과 sync_binlog를 동시에 낮춰도 괜찮은가?** 두 설정 모두 "커밋마다 디스크에 fsync"를 포기하는 대신 성능을 얻는 트레이드오프다. 이 DB는 쓰기가 60초 주기 집계와 트리거 몇 개 수준으로 적고, replica를 쓰지 않으며, 장애 복구도 binlog 기준으로 하지 않기 때문에 허용 범위로 판단했다 — 쓰기가 잦거나 binlog 기반 복제/복구에 의존하는 DB라면 같은 결론을 내릴 수 없다.
